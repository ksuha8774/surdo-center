# Формы оформления врачебных приёмов

## Назначения существующих услуг

| Услуга | Код формы | Состав | Модули |
|---|---|---|---|
| Первичный приём врача-сурдолога | primary, v1 | Жалобы, анамнез, осмотр, заключение, рекомендации | — |
| Повторный приём врача-сурдолога | repeat, v1 | Текущие жалобы, динамика, осмотр, заключение, рекомендации | История доступна общей кнопкой |
| Диагностика слуха | hearing_diagnostic, v1 | Заключение, рекомендации | Существующая аудиометрия и её СППР |
| Консультация по результатам обследования | results, v1 | Причина, интерпретация, заключение, рекомендации | История обследований |
| Краткая консультация | brief, v1 | Причина, результат, рекомендации | — |
| Расширенный приём | extended, v1 | Минимальная форма: причина, результат, рекомендации | Специальные разделы требуют согласования |

Неизвестные услуги получают явно сохранённый код `basic`, без вымышленных обязательных клинических полей, с уведомлением о необходимости согласования.

## Архитектура и хранение

Новых предметных моделей нет. `Service` дополнен полями `medical_form_type` и `medical_form_version`. Назначение меняется в административном справочнике услуг; код и версия проверяются по реестру. Имена услуг используются только один раз при миграции существующего справочника, но не для выбора формы во время работы.

`MedicalVisit` дополнен `form_type`, `form_version`, `form_snapshot` и `additional_data`. Связь документа с пациентом, врачом и услугой проходит через существующий `appointment`, статус — через `completed_at` и статус записи. При первом открытии фиксируется полный снимок конфигурации, включая поля, подписи, порядок, обязательность и модули. Черновики и завершённые документы используют собственный снимок. Изменение назначения услуги не меняет их интерфейс.

Общие текстовые данные остаются в прежних пяти столбцах. `additional_data` предназначен только для согласованных дополнительных полей с префиксом `extra_`. Измерения, аудиограммы и результаты СППР остаются в существующих моделях аудиометрии. В истории пациента подписи берутся из снимка документа; ранее введённые значения не скрываются.

Формы собираются одним `MedicalVisitForm` и общим шаблоном с компонентом поля. Типы ввода: многострочный и однострочный текст, число с границами, дата и выбор из списка. Правила задаются только декларативно; код из конфигурации не исполняется. У разделов и полей порядок определяется порядком списков.

## Расширение и версии

Реестр: `medical/configurations.py`. Опубликованную версию менять нельзя: следует зарегистрировать новую конфигурацию с новым номером, затем назначить её нужным услугам. Вызов `get_configuration()` возвращает независимую копию. Для новой специальности добавляется согласованный состав полей или новый модуль, без замены обработчика приёма и страницы целиком.

Обязательные поля проверяются только при завершении. `completion_modules` позволяет явно требовать завершённую аудиометрию для конкретной конфигурации; для текущих услуг такое требование не включено. Черновики допускают неполное заполнение. Завершённые приёмы нельзя изменить повторным POST; операции приёма сериализуются блокировкой записи.

## Совместимость и аудиометрия

Миграции добавляют столбцы и назначения услуг. Существующие заполненные или завершённые документы получают замороженную форму `legacy`, сохраняющую исходный смысл всех пяти полей. Пустой незавершённый документ связывается с формой услуги при первом открытии. Исходные медицинские тексты не преобразуются и не удаляются.

Кнопка аудиометрии сохраняет черновик перед переходом. Повторное обращение к маршруту создания открывает существующее обследование. Блокировка строки приёма защищает и одновременные запросы. Возврат из обследования ведёт к текущему приёму. СППР запускается только существующим явным действием врача.

Модель `DoctorService` в текущем проекте отсутствует. Существующий механизм проверки принадлежности записи врачу и ролевые ограничения сохранены; новые ограничения по названию специальности не добавлены.

## Перенос

Порядок переноса не изменился: `prepare_transfer.bat` → копирование проекта с `.transfer` → `deploy_new_laptop.bat`. PostgreSQL-резервная копия включает новые столбцы и снимки. Сценарий развёртывания применяет миграции, в том числе после восстановления старой копии базы. После этой доработки нужно заново выполнить подготовку переноса, чтобы получить актуальную резервную копию.

## Ограничения

- Специализированные разделы расширенного приёма пока не согласованы.
- Реестр редактирует разработчик; визуального конструктора форм нет.
- Подключены два известных модуля: аудиометрия и просмотр истории обследований. Новые предметные модули требуют реализации адаптера.
- Документы, начатые до внедрения системы, намеренно сохраняют прежнюю форму `legacy`.
- Проверка на физическом втором ноутбуке возможна только после фактического переноса.

- В браузере на отдельной базе с вымышленными данными открыты все шесть типов услуг. Сняты первичная, краткая, диагностическая формы и консультация по результатам.
- Проверены 1648×928 и мобильная ширина 390 px; первичная форма помещается на одном экране, краткая и диагностическая формы не создают пустую вторую колонку.

- Перед рабочими миграциями создана локальная копия `.local-backups/before_service_forms_20261118.backup`.

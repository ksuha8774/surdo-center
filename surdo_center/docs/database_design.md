# Актуальная модель данных и подготовка интеграции

## Принятые решения

- Существующая Django Authentication сохранена. `accounts_user` остаётся учётной записью, а `accounts_doctor` — профиль врача с отношением один к одному.
- Физические Django-таблицы не переименовываются: это уменьшает риск миграций. ER-диаграмма показывает их реальные имена.
- Дни недели хранятся в формате Python/Django `0..6`, где понедельник — `0`.
- `slot_duration_min` безопасно переименовывается в `booking_step_minutes`; значение существующих строк сохраняется.
- Продолжительность новой записи определяется услугой. Цена и временные границы фиксируются в записи и не меняются вслед за справочником.
- Несколько перерывов в один день поддерживаются отдельными строками исключений. `is_available=True` обозначает дополнительное рабочее время, `False` — блокирующий интервал; полный выходной хранится без времени.
- Пересечения действующих записей запрещены одновременно серверной логикой и PostgreSQL exclusion constraint. Отменённые записи исключены из ограничения.
- Неполная заявка с сайта не превращается в фиктивного пациента: она хранится в `integrations_externalbookingrequest` до сопоставления администратором.
- СППР и филиалы не изменялись. Реальные HTTP/API-вызовы отсутствуют.

## Подготовка к YCLIENTS

`integrations_externalsystem` хранит внешний источник. Отдельные таблицы сопоставляют врачей и услуги с внешними ID. Запись содержит источник, пару `external_system + external_booking_id`, состояние синхронизации, последнюю ошибку и время успешного обмена. Уникальная пара защищает от повторного создания одной внешней записи.

`integrations_syncevent` предоставляет ключ идемпотентности, внешний ID события, направление, статус, контрольную сумму и текст ошибки. Это база для повторных попыток, дедупликации webhook и предотвращения циклической обработки; сам обработчик и сеть пока не реализованы.

## Подтверждение доступности

До изучения договора и API нельзя считать локальную запись гарантированным внешним бронированием.

Рекомендуемая схема:

1. Для записи, пришедшей из YCLIENTS, подтверждающей системой является YCLIENTS; АСУ принимает уже созданное бронирование и проверяет локальный конфликт.
2. Для записи, созданной в АСУ, при наличии API запись сначала получает состояние `pending`. Подтверждённой она становится только после успешного ответа YCLIENTS.
3. При конфликте локальная транзакция не должна молча перезаписывать внешнее состояние. Событие фиксируется как `error`, интервал требует повторной проверки или решения администратора.
4. Повторный webhook определяется по `(external_system, external_event_id)`, а повторная запись — по `(external_system, external_booking_id)`.

## Варианты синхронизации расписания

1. **YCLIENTS — источник истины.** Безопаснее для уже работающей онлайн-записи, но локальные изменения графика должны быть запрещены либо отправляться во внешний сервис до вступления в силу.
2. **АСУ — источник истины.** Удобно для внутренних процессов, но возможно только если API позволяет полноценно менять графики и исключения.
3. **Разделённое владение.** Например, регулярный график задаётся в YCLIENTS, а локальные медицинские блокировки — в АСУ. Самый сложный вариант: необходимы правила приоритета и объединения интервалов.

Конкретный вариант пока не выбран. Синхронизировать потребуется отдельно регулярные графики, исключения/перерывы и записи пациентов.

## Миграции и обратимость

Миграции не применяются автоматически. Переименования сохраняют колонки, специализации копируются в профиль врача, а плановые цены существующих записей — из связанной услуги. Перед exclusion constraint миграция проверяет существующие пересечения и останавливается без удаления данных, если они найдены.
